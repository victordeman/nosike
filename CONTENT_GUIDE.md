# Content guide — what each file controls

All site text and data lives in `content/`. Pages are built from these files at deploy time; nothing else needs to change when you edit them. Every record has a `"source"` field saying where the fact came from — always fill it in (e.g. `"Client email 2026-11-25"` or `"CV › PUBLICATIONS"`).

**Golden rules**

1. Edit on a **branch** and open a **pull request** — never commit straight to `main` (see [`EDIT_WORKFLOW.md`](EDIT_WORKFLOW.md)).
2. If the Vercel **Preview** build fails, the content is invalid — the error message names the file and field. Fix and push again.
3. Never publish phone numbers, personal email addresses, birth dates, family details, home address, referees or religion — the privacy check rejects the commit.
4. `id` values must be unique within their file and never reused after deletion (they appear in page URLs for talks/events).
5. When in doubt about a fact, set `"status": "pending"` (or leave the record out) instead of guessing — pending items are hidden from the public pages.

## Adding a publication (`publications.json`)

Append an object to the array. Two shapes exist, chosen by `"kind"`:

Book:
```json
{
  "id": "pub-2026-example-book",
  "title": "Title of the Book",
  "authors": ["Nosike, Austin N."],
  "year": 2026,
  "kind": "book",
  "publisher": "Publisher name",
  "place": "Lagos",
  "isbn": "978-...",
  "role": "author",
  "source": "Client email 2026-11-25"
}
```

Article / chapter / paper:
```json
{
  "id": "pub-2026-example-article",
  "title": "Title of the Article",
  "authors": ["Nosike, Austin N.", "Co-Author Name"],
  "year": 2026,
  "kind": "journal-article",
  "venue": "Journal Name, Vol. 1, No. 2",
  "publisher": "Optional publisher",
  "issue": "Vol. 1, No. 2",
  "pages": "1-15",
  "source": "Client email 2026-11-25"
}
```

- `kind` must be one of: `book`, `journal-article`, `book-chapter`, `conference-paper`, `monograph`, `report`, `thesis`, `lecture`, `working-paper`, `unpublished`.
- `year` may be `null` for undated works (they sort last).
- `role` is only for books: `author`, `editor` or `unknown`. **Do not claim authorship unless confirmed** — `unknown` shows no author claim in search metadata.
- Theme tags are derived automatically from the title via `themes.json`; unmatched titles land under "Other" (listed in `OPEN_ITEMS.md`).

## Adding an honour (`honours.json`)

```json
{
  "id": "hon-example-2026",
  "title": "Name of the award or fellowship",
  "year": "2026",
  "issuer": "Awarding body",
  "status": "approved",
  "source": "Client email 2026-11-25"
}
```

`status`: `approved` (published), `pending` (hidden until confirmed), `omit` (kept for the record but never shown — used for disputed items like the removed West Coast award).

## Adding a conference / event (`conferences.json`)

```json
{
  "id": "conf-example2026",
  "code": "EXAMPLE2026",
  "name": "Conference name",
  "dates": "12–14 March 2026",
  "venue": "Venue, City",
  "role": "Chair; lead editor",
  "status": "verified",
  "source": "Proceedings PDF / client confirmation"
}
```

`status` is `verified` (shown) or `pending` (hidden). Use `pending` whenever dates or venues are not confirmed by a source document — see the Rivers State 2012 entry for the pattern.

## Adding a talk (`talks.json`)

```json
{
  "id": "talk-example-2026",
  "title": "Talk title",
  "date": "2026-05-10",
  "venue": "Venue, City",
  "kind": "lecture",
  "abstract": "One-paragraph neutral description (no claims from slide decks).",
  "status": "verified",
  "source": "Client confirmation"
}
```

`kind`: `lecture`, `conference`, `talk`, `presentation`.

## Adding a career role (`career.json`)

```json
{
  "id": "career-example-2026",
  "institution": "Institution name",
  "place": "City, Country",
  "country": "Nigeria",
  "dates": { "start": "2026", "end": "present" },
  "title": "Role title",
  "subRoles": ["Additional responsibility"],
  "kind": "academic",
  "source": "Client CV / appointment letter",
  "verified": true
}
```

`dates.start`/`end` are 4-digit years; `end` is `"present"` for current roles. `kind`: `academic`, `visiting`, `pre-academic`. Visiting professorships need dates from a source before `verified: true`.

## Editing bios (`bio-short.mdx`, `bio-long.mdx`)

Plain Markdown. Word limits are enforced by the build (short ≈ 100 words, long ≈ 500). Both files carry front-matter with an approval flag; remove the `approval: client approval pending` line only after the client has approved the text.

## Changing photos

Photos are **not** edited by hand. New photos go to `_sources/photos/` locally (never committed), then:

```bash
node scripts/optimise-images.ts   # writes public/images/* and content/images.json
```

A developer then assigns the new image id in `src/` (hero, about, gallery) and sets the right `role`/`galleryCategory` in `content/images.json`. The privacy and EXIF checks run automatically. For print-resolution media-kit downloads, request the original high-resolution files from the client — the pipeline sources are ~750 px wide.

## After editing

1. Commit on your branch, open a PR, wait for the **Vercel Preview** check.
2. Open the Preview link and check the affected page(s).
3. Merge only when the preview looks right — merging deploys to the live site within minutes.
